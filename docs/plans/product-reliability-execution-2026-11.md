# 产品可靠性改造：执行清单与记录模板

编写日期：2026-11-08。2026-11-10 状态：**D0–D4 本轮适用开发范围已有交付记录；下文保留执行步骤与模板，当前状态以[进度记录](product-reliability-progress-2026-11.md)为准**。

本页将[主计划](product-reliability-next-step-2026-11.md)的已确认方向展开为工作步骤。主计划负责范围、行为契约、指标口径和验收标准；本页负责执行顺序、交付物及记录格式。首次执行从 D0 开始；恢复已有工作时，先核对最后一份交接收据，再进入其中指定的切片。

## 1. 排期、分工与交付位置

按一人维护安排，一次推进一个变更切片。执行 Agent 负责事实核查、方案、获授权的实现与合成回归；维护者负责实际使用反馈、本人签收和范围取舍。已授权切片中的必要步骤连续完成，新增范围按主计划处理。

| 顺序 | 开始条件 | 本段交付 | 出口与下一步 |
| --- | --- | --- | --- |
| D0 候选与范围 | 已选定工作树，获得调查任务 | 候选表、状态矩阵、D1 任务卡、待核实清单 | 按主计划 §9.2 判断 D1 准备条件；存在影响 D1 的未知项时先补证 |
| D1 配置与模型 | D0 已明确目标、写入范围及回归，已获 D1 实施授权 | 配置路径收据、实际障碍的修复、配置说明更正 | 主计划 §4 中配置相关用例闭合，交接 D2 |
| D2 任务与恢复 | D1 配置路径通过，任务验证候选固定，工作在授权范围内 | 分入口生命周期矩阵、恢复操作说明、对应回归 | Web Runtime 保证有证据；QQ 实际能力和缺口单列 |
| D3 界面与交付指南 | D1、D2 核心路径通过，Linux + Docker 目标已登记 | 最小交付指南、合成安装/升级/恢复收据、本人界面意见 | 关键路径范围通过后，维护者可按主计划启动核心观察 |
| D4 可信插件 | 固定插件候选、原失败材料及本人审核范围 | 原失败裁决、生命周期回归、包审核与治理记录 | D4 通过才将对应市场安装/更新能力纳入试用 |
| 使用观察 | 核心阶段出口满足，维护者选定范围 | 基线、阈值记录、正式观察摘要、第 2/4 周结论 | 通过、不通过或证据不足；实际障碍进入下一轮单问题改造 |

D0–D4 按阶段出口推进，不预设未经估算的完成日期。执行者接手时登记本切片下一次交付点；遇到阻塞时记录已完成部分、影响范围与解除动作。核心观察期间可继续处理 D4，但市场未就绪的能力保持排除；候选变化按主计划分段计量。

每次执行在私有工作区建立独立证据目录，建议形状为 `<workspace>/review-artifacts/product-reliability/<run-id>/`。目录包含一份入口报告和引用的合成验证收据，不修改历史证据。公开文档只保存脱敏结论；真实配置、凭据、消息及成员数据不进入执行材料。

## 2. D0：固定候选与下一步范围

依次完成：

1. **工作树核对。** 读取工作区入口和当前仓库规则，记录真实路径、分支、源码 SHA、完整树、已有修改及未跟踪文件；明确本次写入边界。沿已有发布/部署报告定位公开快照与产物，各自保留核对时间和哈希。未刷新远端或线上时明确标为历史记录。
2. **环境核对。** 确定 Linux 系统、CPU 架构、Docker 运行条件、实际镜像与持久化挂载形状、前端提供方式及资源约束。以现有纯产物路线为基准，定位安装和回退所需材料；只读核对不得变成重启、迁移或改配置。
3. **状态盘点。** 按主计划 §9.1 登记 D0–D4、#148/#151/#152 及 Python 平台证据；逐项关联候选与入口。特别保留 #152 原回放 52/53、exit 1，不能用补证或总 CI 结果替换原结论。
4. **说明与证据校正。** 逐项处理主计划 §3 的五处差异。对 POSIX，区分 CI 登记、精确候选实际运行、目标容器覆盖；查不到运行收据时留下明确的查询目标与影响切片，不推断成功或失败。
5. **D1 任务具体化。** 沿主计划 §5.1 查明当前配置调用链，选定第一个要确认或修复的行为，填好本页 §9 的任务卡。已有行为满足要求时，安排缺失验证或说明更正；不为了产生代码差异虚构缺陷。

**交付检查：**另一位执行者能从报告找到当前候选、历史反例、待核实事实和 D1 起点。D0 清单可以携带不影响 D1 的未知项交付；D1 的候选、契约或写入范围仍不清楚时，下一动作必须是补证。D0 收据不会自动授权产品改动。

## 4. D2：提交、审批、取消与中断恢复

先分别建立 Web ZBA、QQ `//` 和聊天入口的能力表，再处理适用场景；Web 的台账结论不自动覆盖其他入口。

| 步骤 | 工作 | 必须核对的行为 |
| --- | --- | --- |
| D2.1 受理与核对 | 覆盖正常提交、提交响应丢失、原键 Find 和同意图重复请求 | 区分已受理、未受理和无法证明；同一原意图不因核对而变成新任务 |
| D2.2 审批 | 覆盖批准、拒绝、过期和取消相关竞争 | 未获批时合成执行器副作用计数为零；决定沿原任务收口，审批残留可解释 |
| D2.3 取消与超时 | 观察取消请求、终态、迟到结果及执行器收到取消的情况 | 状态收口与外部动作结果分别记录；无法证明副作用结果时保留未知，禁止自动重做 |
| D2.4 重连与身份 | 制造事件缺口、网络恢复、锁定/过期及换身份 | 资源重读成功后推进游标；旧身份的迟到结果不污染当前身份，秘密输入按规则清除 |
| D2.5 宿主重启 | 在隔离合成环境重启候选，覆盖待批和已派发任务 | 按现有契约解释失效/Unknown；核对原记录，不重放不确定副作用 |
| D2.6 QQ 实际路径 | 用适配该入口的合成场景核对完成、失败及实际提供的取消/恢复能力 | 列出已证实、未验证和不具备的能力；审批受控操作仍限定 Web |

**恢复说明按操作顺序写：**先找原操作关联，再查当前权威状态，核对能证明的副作用，最后说明可继续的动作或需要维护者介入的原因。丢失原键且现有机制不能证明原操作结果时，明确这一限制；普通配置回读不充当原操作回执。

**交付物：**分入口生命周期矩阵、合成恢复证据、面向操作者的恢复说明，以及关键界面需要本人验证的具体步骤。矩阵保留每个场景的入口、预期、实际结果、证据、未决项；受影响的核心场景未通过时不进入该范围的真实观察。

## 5. D3：Linux + Docker 交付与关键界面

复用 [Runtime 部署说明](../operations/agent-runtime-deployment.md)、[回滚预案](../operations/rollback-playbook.md) 和 [#148 清单](../acceptance/issue148-inventory.md)，按以下顺序形成最小交付指南并验证：

1. **准备安装材料。** 对照 D0 目标列出所需产物、镜像、依赖、目录与端口用途、独立前端及访问路由、管理员首次配置方式。构建发生在准备环境，低内存目标沿 [Dockerfile.app](../../Dockerfile.app) 接收产物；不能混用源码镜像路线。
2. **干净启动。** 使用全新合成数据根，维护者按指南完成安装、启动、管理员访问、模型配置和一次合成任务。分别检查服务状态、前端资源、认证结果与配置应用，记录实际命令和结果。
3. **升级与恢复演练。** 在同一隔离环境建立合成旧状态，按已有预案备份、升级、停写恢复并重新核对配置和任务状态。记录用到的产物与数据快照、恢复步骤及结果；仅容器启动成功不能代替数据恢复证据。
4. **关键界面签收。** 固定候选和图组，由维护者走配置、任务、审批/取消与恢复路径，检查中文提示、窄屏、键盘、焦点和关键错误提示。使用合成界面收集意见；全站视觉、原生缩放与市场界面只按实际覆盖单列结论。
5. **形成交付结论。** 列出指南已走通步骤、失败步骤、本人意见和未覆盖环境。Linux 原生、Windows 正式部署及未选架构仍在本轮承诺外；真实 QQ 接通、公开发布和线上部署另留结果。

**交付物：**可逐步照做的指南、Linux + Docker 安装/升级/恢复收据、关键界面签收表、核心观察范围清单。D0–D2 和关键 D3 通过后，维护者决定是否启动该范围观察；D4 未完成时排除市场安装/更新。

## 7. 使用观察：准备、基线、正式样本与收尾

这部分从维护者登记的观察起始日计时。基线和正式样本使用同一份观察日历；冻结阈值、暂停或变更候选都不自动重置第 4 周收尾日期。

| 时点 | 执行动作 | 留下的记录 |
| --- | --- | --- |
| 开测前 | 维护者选定三类代表任务、实际入口及预期；执行者用合成样本检查安全采集字段、去重口径与计量覆盖 | 范围、候选/配置、启用能力、起止日期、现有额度、采集来源和已知盲区 |
| 基线窗口 | 记录所选入口的状态、时延、用量覆盖、人工耗时和结果评价 | 基线样本量、缺失项、分母与分布；不提前填写达标结论 |
| 基线后、正式样本前 | 维护者确定阈值及适用范围，固定抽样方法、版本和冻结日期 | 可判断通过与否的阈值表；有用性、等待、成本的口径及不可计量项 |
| 正式观察期间 | 按日保存白名单汇总；异常按主计划暂停/恢复；候选及重要配置变化分段 | 新样本、在途/未知计数、暂停和恢复决定、变更影响及对应回归 |
| 每周 / 第 2 周 | 复核样本完整性、常见阻碍、维护成本和本人评价；第 2 周决定结束、继续、缩小范围或先修问题 | 带范围和依据的周结论；若提前结束，同样说明通过、不通过或证据不足 |
| 最迟第 4 周 | 对固定候选、范围和阈值形成结论 | 范围内通过 / 不通过 / 证据不足，以及继续使用或下一切片的具体理由 |

阈值与采集覆盖未冻结前不进入正式验收窗口。某项无法可靠计量时，明确缺失和对结论的限制；不能用零值、其他入口计数或总账单代替。新样本仍不足时按证据不足收尾，补采另定范围和结束条件。

**观察准备表的最小字段：**范围版本、候选/重要配置版本、入口、任务类别与预期、采集来源与字段白名单、任务/事件去重方式、分母定义、缺失识别方法、有用性抽样方法、现有额度、起止日期、阈值版本和冻结日期。分别记录“开测前固定”与“基线后冻结”的字段，避免倒填标准。

**每日摘要的最小字段：**日期、候选/配置、入口/任务类别、样本集合编号、提交尝试/拒绝/已受理/受理未知、受理任务的终态/在途/Unknown 分布、可计量时延的覆盖数、已知用量与未知数、有用性抽样及未评价数、人工返工/维护耗时、异常和证据位置。

样本集合编号是观察材料自定义编号，不写真实会话/成员/任务标识。跨日任务以同一受理集合追踪结局，日摘要不能相加为重复的受理数；进程重启注明计数器世代。耗时、成本和用量的具体分母与排除项遵守主计划 §6。

**下一轮改造只选择一个问题：**用频率、影响程度、恢复耗时和改动风险排序，附独立反例及受影响入口；沿主计划阶段三形成任务卡。核心观察结论不会自动扩大插件、平台或外部试用范围。

## 9. 可直接复用的任务与交接模板

### 9.1 单切片任务卡

| 字段 | 填写要求 |

### 9.3 切片交接

交接正文按六项填写：**本次范围；已完成及证据；失败与未覆盖；本人待办；当前变更与回退；下一步及其前置条件。** 完成结论逐项限定到实际入口、平台和候选；源码存在、宿主采用、合成回归、本人签收、发布及部署各自保留状态。

若未满足出口，交接写清已经做到哪里和最小解除动作，保留原证据。若满足出口，指出下一张任务卡；不以“整体已绿”替代范围。

## 10. 本轮最终交付的组成

整个改造阶段收尾时，应能从一份入口报告访问：候选与状态矩阵、D1 配置证据、D2 恢复证据、D3 指南与本人签收、D4 已完成部分及排除范围、观察结论、遗留问题与下一轮任务卡。

核心范围通过而某专项仍未签收时，按主计划分别给出结论。文档可复现、合成验证通过、真实使用有价值、公开发布完成和线上部署完成不是同一项声明，分别引用对应收据。
