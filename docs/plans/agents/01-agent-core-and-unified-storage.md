# Agent-01：Core / Storage 与统一保存契约（Why / What / How）

> 修订：2026-10-07，第二版；Wave 1。
> 状态、准入、写权、测试命令和证据模板统一见[执行总纲](00-orchestration-and-dependency-graph.md)。
> 本手册是目标要求，不宣告当前实现完成；代码施工须另获授权。

## 一、为什么（Why）

领域端口与持久化细节分离，才能复用已有能力并支持独立 ZBA。旧版把分区读写接口当作全局原子保存，遗漏版本冲突、秘密字段和应用失败语义，本版先定义行为契约再选接口名称。

## 二、做成什么样（What）

### 2.1 输入与边界

- 先查 Core 的 Ports / Plugins、现有 SettingsStore、SettingsBox.ApplyPersisted、秘密仓储及数据库事务入口。
- Core 保留领域和应用端口，不依赖具体 IO 实现；Storage 仅引用 Core。
- IUnifiedConfigurationStore 是旧方案中的拟建名称，当前未找到定义。可以复用或扩展现有端口；确需新增时记录不能复用的原因、消费者和兼容策略。
- 管理契约须覆盖已登记插件、驱动实例、模型的稳定标识、能力、状态、配置校验及不支持的动作；不凭统一外观强制所有能力都支持启停或连接测试。
- 首阶段插件实现归 Engine；Core 只放被多个模块消费的必要契约。

### 2.2 保存语义（需求，不是已实现 API）

| 场景 | 必须明确的结果 |
| --- | --- |
| 读取 | 非秘密快照、配置版本、字段生效规则 |
| 整批修改 | 字段及跨模块校验全部成功后提交；任一失败不部分提交 |
| 并发修改 | 比较基准版本；冲突不覆盖新值，返回可重新读取的状态 |
| 空值 | 缺省、显式清空、删除与保留分别定义；未知字段/分区拒绝 |
| 重复请求 | 明确幂等键作用域、有效期和相同键不同参数的冲突规则 |
| 秘密 | 元数据不回显值；保留、替换、删除显式区分 |
| 提交与发布 | 持久化成功后发布快照；后续应用失败返回“已提交但未应用/需重启” |
| 重启 | 已提交版本可恢复；不能依赖仅内存修改 |
| 变更记录 | 记录安全字段、版本和结果；不包含秘密与群聊正文 |

QQ 官方 Secret 继续只从环境变量读取，面板不接收、保存、导出或回显。统一保存不能悄悄扩大秘密管理范围。

事务边界应覆盖本批配置、版本及必要的安全审计元数据；环境变量和外部文件不能伪装成同一个 SQLite 事务。需要多存储介质时先设计原子性边界与恢复方案，由 00/06 确认，不宣称跨介质全局原子提交。

### 2.3 配置真源与过渡

行为配置当前由 SQLite settings 表承载；旧 JSON 导入不是持续覆盖数据库的机制。先保持既有有效写入路径。未来若采用文件编辑，文件只能作为经过校验、版本检查和统一保存的导入输入；明确谁导入、何时生效、失败如何报告及哪些字段需重启。未经此流程验收，不得推荐手改数据库或任意 JSON 后重启。

## 三、如何实施（How）

1. **接口盘点**：提交现有类型、消费者、重复实现及拟迁移路径清单；完成条件是每项管理/保存需求都有现有入口或明确缺口。
2. **契约评审**：与 02/03/04/05/06 确定 DTO、端口和上述语义；00 登记契约版本后才写消费代码。
3. **实现与迁移**：迁移 Storage 实现并保留兼容读取；通过共享文件合入流程接入宿主，确认不会产生两套独立数据库单例或写入协调器。
4. **合成验证**：覆盖成功保存、整批失败、版本冲突、秘密保留/删除、发布失败、重启恢复、旧格式迁移和并发写入。
5. **交付**：依总纲提交宿主调用链与当前证据；单独构建 Storage.dll 不足以验收。

写权：Core / Storage 内已认领路径；契约变更经消费者确认；旧 Headless 源码、宿主项目引用及共享设置文件由 00 统一合入。测试文件先登记，不越界修改。

## 四、验收与停止条件

- [ ] 目标依赖成立；Core 的 IO 边界及 Storage 的事务入口有跨工程护栏。
- [ ] 宿主真实采用迁移实现；旧实现删除前有等价行为和兼容证据。
- [ ] 全局保存的并发、原子性、秘密及提交/应用区分通过合成测试。
- [ ] 配置真源、现有运维路径与未来导入方案不矛盾。
- [ ] 执行总纲的适用基线及新增存储测试通过，证据可复现。

无法保持保存通路、事务跨介质未定义或出现未知数据兼容性时停止接入。测试命令只使用真实存在的工程，新增测试落地后把准确命令记入交付记录，不预先造测试名。
