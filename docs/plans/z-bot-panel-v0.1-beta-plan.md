## 一、项目概述

Z-bot Panel 是 Z-bot 的交互式 WebUI，通过 **Z-bot Backend API（ZBA）** 获取运行状态、管理配置和展示 Agent 任务。项目要做到：用户能够方便地管理机器人，也能够用自然对话让机器人调用已开放的能力完成工作。

为什么要重新设计：现有功能分布在多处，用户需要知道配置位置和操作方式；自然对话里的工具能力已有基础，但需要统一能力发现、权限控制、执行反馈和失败处理。新的面板负责把这些能力整理成清楚的操作流程，后端负责实际执行和保存。

最终体验围绕三条主线展开：

- **看状态**：打开面板即可知道机器人、平台驱动、插件和模型是否正常，异常有原因和处理入口。
- **改配置**：按功能找到配置，修改后明确看到“未保存”“已保存”“已生效”或“需要重启”，刷新后结果一致。
- **让 Agent 干活**：自然语言提出任务，看到执行进度、必要的审批和最终结果；失败时知道原因和下一步。

例如，用户说“帮我看看 example.com 上这篇文章讲了什么”，在网页读取工具已配置、已授权且可用时，Agent 应当完成读取与摘要；工具不可用时应说明限制。提醒等尚未验收的能力不作为首版承诺，只有能力真实存在、接入且通过测试后才对用户开放。

### 范围与前后端边界

后端采用 .NET 8 模块化单体：核心模块以独立程序集分层，运行时由 Headless 统一组装。ZBA 是后端 HTTP 接口边界，既负责 Web 所需的接口，也必须能由合成测试或其它客户端独立调用。API 适配层拟放入 `src/BotAgent.Panel/` 工程，由 Headless 同进程承载，经 Core 应用端口调用能力，不直接访问数据库。Agent-06 负责实现；工程命名若调整，由 Agent-00 登记并同步引用。首阶段插件放在 Engine 内部，不另建 Plugins 工程。

前端拟建于 `src/web/`，独立依赖、独立构建、独立发布；框架在后端契约稳定后确定。前端只通过 ZBA 交互，不引用 C# 实现、不直接访问数据库、不承担权限裁决，不要求重新构建后端才能发布页面。后端启动、配置保存和 Agent 执行不依赖 Web 静态资源。开发与生产使用统一的 API 基址约定，避免将某个开发端口写死在页面里。

首版范围以下文能力表为准。MCP 管理页可延期；只有对应后端验收且负责人明确纳入本次范围后才开发。第三方市场、任意容器创建、Docker 高权限管理与远程部署均不自动纳入首版。

## 二、设计要点

### 1. 以用户任务组织面板，让状态和操作结果清楚可见

**做成什么样：** 使用“概览、能力管理、配置、Agent 任务”作为建议入口。状态显示可用、停用、待配置、连接失败等真实状态；配置修改集中显示未保存内容与保存结果；任务展示等待、执行、待审批、成功、失败、取消请求中、确认取消或结果未知；具体状态字段在 ZBA 契约评审时冻结。

**怎么做：** 页面依据后端提供的描述、状态和配置元数据生成交互，错误定位到具体字段或具体能力。移动端能够完成查看状态、修改配置和审批等主要操作。弹窗关闭、切页和刷新均有明确的未保存处理方式；具体视觉和交互方案留到 Web 阶段评审。

**为什么：** 用户关心机器人能否正常工作、改动是否生效、任务是否完成。这些信息应当直接可见，减少记忆命令与寻找配置的成本。

**页面职责建议：** 导航名称可在 Web 阶段调整，但每项能力只有一个主要编辑入口；概览与快捷入口复用同一状态和草稿，不另建一套保存逻辑。

| 入口 | 用户要解决的问题 | 首版内容与边界 |
| --- | --- | --- |
| 概览 | 机器人现在是否可用，哪里需要处理？ | 整体及分项状态、最近更新时间、安全错误摘要、跳转入口；不把真实聊天内容当诊断信息展示 |
| 能力管理 | 某个平台、插件或模型为什么不可用？ | 全部已登记项的能力和状态、适用的管理动作；区分未配置与故障，不支持的动作说明原因 |
| 配置 | 我改了什么，是否保存和生效？ | 当前授权范围内的配置草稿、校验、变更摘要、统一保存与生效反馈；秘密遵循专门规则 |
| Agent 任务 | 请求进展如何，需要我批准什么？ | 任务提交、进度、必要的审批和取消、安全结果及恢复；联调用合成数据，不借用生产会话 |

**跨页约束：** 首次加载显示加载态，无记录显示空态，请求失败显示错误态；断线后保留的旧数据明确标记“尚未刷新”，不能继续伪装为实时正常。重新获取状态是只读操作，不顺带重启服务、重做工具或重新保存。

### 2. 每个插件和驱动都有后端接口，保存通过统一入口完成

**做成什么样：** 每个已登记的插件、驱动实例都可查询标识、描述、能力、配置和运行状态。后端对可管理能力提供启停、配置校验、保存及适用的连接检查；不支持的动作明确声明。模型设置遵循同样的管理方式；MCP 管理页被纳入本次范围时同样遵守。

**怎么做：** 内部优先复用现有插件注册、平台适配器与配置仓储端口，ZBA 将这些能力映射为面板需要的接口。统一保存入口负责整批校验、事务提交、版本检查、审计和运行时发布；分别读取某个配置分区不能替代整批保存的事务语义。保存返回当前版本，以及哪些设置已生效、哪些需要重启。

**为什么：** 面板不必为每种功能另写一套保存流程；同一能力通过面板或其它客户端操作时，权限、校验和结果保持一致。后端内部契约与 ZBA 外部接口都需要验收，只有类接口并不足以完成面板交付。

**交互流程：** 读取授权范围内的快照和版本 → 编辑同一份草稿 → 查看修改摘要 → 提交一次整批保存 → 展示持久化结果及生效状态。保存范围必须明确展示，只包含本次授权可编辑的配置；不能把不可见字段的默认值写回后端。

| 情况 | 页面应怎样反馈 | 下一步 |
| --- | --- | --- |
| 有修改但未提交 | 显示未保存项，切页/关弹窗时保护草稿 | 继续编辑、保存或明确放弃；页面刷新按已声明策略提示，不承诺浏览器一定保留内存草稿 |
| 正在保存 | 表示请求处理中，阻止重复提交同一批次 | 后端仍须去重，不能只靠按钮禁用保证幂等 |
| 字段校验失败 | 定位字段或跨模块错误，保留可修正的草稿 | 修正后重新校验；不显示部分保存成功 |
| 版本冲突 | 告知服务端已变化，不覆盖新值 | 对比安全差异或重新载入，再由用户决定如何处理草稿 |
| 已持久化，尚未全部生效 | 分别显示已保存版本及未应用/需重启项 | 给出处理指引；首版不因此新增远程重启功能 |
| 保存响应丢失 | 显示提交结果待确认，而非直接判失败 | 按契约查询版本或请求结果；确认前不盲目重发，无法确认则保持未知 |

“是否有草稿修改”“是否持久化”“是否运行时生效”是不同维度，可以同时存在；不要合成互斥的单一成功/失败状态。秘密输入不进入本地持久化草稿、URL、前端遥测或错误日志；取消编辑、退出登录后清除秘密输入，重新认证不自动重发旧写请求。默认不承诺跨刷新保存未提交草稿。

**配置开关与即时动作：** 每个控件依据 ZBA 元数据标明“修改草稿，保存后生效”或“立即执行管理动作”。默认不把配置开关点击当作已保存；适用的连接检查、启停等即时动作单独显示执行结果，不混入整批配置事务。是否支持、影响哪些在途任务以及是否需要确认，在契约冻结时逐项说明。

### 3. 让 Agent 通过自然对话使用能力，并提供可信的执行反馈

**做成什么样：** Agent 能选择已登记且获准使用的工具，必要时询问缺失信息或请求审批。面板展示任务摘要、工具名称、耗时、审批状态、经过脱敏的结果摘要与失败原因。

**怎么做：** 在现有有限步进循环与工具目录基础上，补齐能力发现、权限过滤、步数与时间预算、取消、结果审计和后台任务管理。执行审批绑定具体工具、目标和本次参数，不能用一次同意扩大为长期无限授权。后台评估任务有队列上限、异常处理、取消和停机收口。

**为什么：** 智能体的价值要落在已完成的事情上。只有实际成功的工具结果才能支持“已完成”的反馈；连接失败、执行超时与结果未知应分别展示。页面展示可解释的动作摘要，不公开模型隐藏推理或默认展开原始工具载荷。

**任务交互约束：** 以下是用户可见语义，不预设后端枚举或字段：

- 提交请求后，只有后端确认接受并给出稳定任务标识，页面才将其作为已受理任务跟踪；提交响应丢失先查询/去重，不自动创建第二个任务。
- 等待、执行和待审批是运行阶段；审批页展示拟执行动作、目标、经过脱敏的参数摘要和影响。批准与拒绝均由后端绑定本次任务和参数，过期审批不能继续执行。
- 点击取消后先显示“取消请求中”；已经完成的任务不被迟到的取消结果覆盖。远端是否停止无法确认时显示结果未知，不宣称副作用已经撤销。
- 任务阶段与连接新鲜度分别显示。断线不等于任务失败，超时不等于远端动作没有发生；刷新后恢复原任务，而不是重新提交。
- “重试读取状态”和“重新执行任务”是不同动作。后者必须明确告知可能再次产生副作用，并重新经过权限及必要审批。
- 展示结果采用安全的文本/受限格式，不执行工具返回中的脚本或任意 HTML；工具输出中的指令不成为前端控制命令。

## 三、实现方式

### 1. 先完成后端契约、保存体系和运行链路

**现状依据：** 已存在插件生命周期和注册接口、平台适配器、配置仓储端口、先持久化后发布的配置入口，以及有限步进工具循环。当前宿主仍内嵌 Web 静态资源；统一配置新接口、Engine/MCP 新工程及新 ZBA 契约不能视为已经交付。配置当前以数据库为真源，不能直接把“编辑 JSON 后重启”当作有效运维流程。

**施工清单：**

- 由 Core/Storage 负责人核对已有端口并补齐统一管理与保存契约，定义插件和驱动实例标识、配置版本、校验错误、秘密字段和生效方式；统一入口复用当前事务及持久化后发布机制。
- 由 Platforms/Model 负责人核对独立程序集是否被宿主实际使用，验证实例策略、白名单和思考参数；保留 `reasoning_effort: "none"` 的明确语义。
- 由 Engine/MCP 负责人迁移和接入运行链路，保留工具门禁及发送审计，按协议验收 MCP 握手、能力发现、取消和重连。Docker daemon 访问属于高权限能力，不能作为天然沙箱承诺。
- Agent-06 提供宿主集成补丁与只读 CLI，Agent-00 统一合入解决方案、宿主引用及组装根。配置变更是否需要重启必须有明确规则；未来文件导入也必须经过校验及统一保存，不能把任意 JSON 读取当作现有配置通路。

**验收：** 宿主确实使用新的实现；禁用插件时不调用它的工具或外部服务；平台实例间权限隔离；保存失败不发布新配置；重启后能够恢复已保存值；后台任务能够按停机预算收口。每项附当前构建、场景与测试证据，不能只凭历史测试数量解锁下一阶段。

### 2. 完成 ZBA，作为 Web 开工的强制前置条件

**能力范围冻结（首版）：** 下列必选项构成 ZBA 首版门禁；范围变更由项目组记录版本、影响与适用测试。MCP 后端仍按 Wave 4 交付并验收，面板 MCP 管理页可延期；该可选项不免除后端波次验收。未纳入的页面不得模拟能力已配置或可用。

| 能力 | 首版范围 | 核心验收 |
| --- | --- | --- |
| 状态与健康 | 必选 | 无需 Web 即可读取；秘密和群聊正文不出现在状态 DTO |
| 插件与驱动管理 | 必选，覆盖全部已登记项 | 每项有稳定标识、描述及真实状态；未知或不支持的动作明确拒绝 |
| 配置读取与保存 | 必选 | 返回非秘密配置快照与版本；旧版本冲突不覆盖新值；整批失败不部分提交；保存与生效状态分别返回 |
| 模型管理 | 必选 | 安全元数据、连接检查与运行状态；凭据不回显；QQ 官方 Secret 只从环境变量读取，面板不得接收、保存、展示、导出或回显 |
| Agent 任务、审批与取消 | 必选 | 任务标识与终态真实可查；过期或拒绝审批不执行动作；取消状态不冒报 |
| 事件流 | 必选的状态恢复语义；SSE 传输可选 | 即使不用 SSE，也可查询任务终态及恢复遗漏事件；若采用 SSE，须具序号/恢复、心跳和断线处理；断线不自动重做工具调用 |
| MCP 管理 | 可选，启用前需独立批准范围 | 若纳入首版，须满足独立的凭据不回显、执行端治理、连接生命周期与契约测试；未纳入则不得出现在“已支持”体验中 |
| Docker/本地高权限承载 | 首版范围外 | 另行安全评审和发布批准，不作为通用 MCP 管理的默认能力 |

**责任及写权限（已采纳）：** Agent-06 从前期参与 ZBA 契约设计，在 Wave 5 承担 ZBA 与宿主集成验收；Agent-00 负责共享文件最终合入及证据核对，负责人决定 Web 解锁和最终发布。Agent-07 在解锁后承担独立 Web。拟建 Panel 工程由 06 维护，解决方案、宿主引用和组装根由 00 写入；临时写权移交遵守执行总纲，不能同时认领。总规划和手册 00/06/07 使用同一门禁。

**范围及日期决策：** 负责人于本轮确认首版范围与上述分工；具体接口仍待评审。2026年10月10日至11日保留为有条件目标窗口，任一强制门禁未通过即顺延，使用日期依据证据另行批准。范围变更由负责人确认并登记影响，不能由 Agent 自行缩减必选能力换取按期交付。

上表是**范围已确认、实现待验收的能力要求**，不是现有路由清单。具体路径、认证方案、DTO 和错误码在后端施工前评审并记录到 OpenAPI。

**保存数据流：** 客户端提交修改及基准版本 → ZBA 认证与授权 → 应用服务进行字段和跨模块校验 → 事务内提交配置、版本和审计 → 持久化成功后发布配置快照 → 返回提交版本及生效信息。运行时应用失败时保留真实提交结果，明确报告未应用或待重启，不能伪装成数据库未提交。

**边界约束：** 缺省字段、显式清空、删除凭据和保留凭据的语义分别定义；未知分区、未知字段、过大请求和无权限请求均拒绝。重复写请求和审批动作有幂等或去重规则。后端决定安全策略，前端只负责交互；Cookie 认证下明确 CSRF 防护，跨域及流认证按照最终认证方案验证。

**开工门禁：** ZBA 的上述首版范围通过合成数据契约测试，认证与授权、并发保存、事务失败、重启恢复、事件恢复、取消及秘密不回显均有证据。OpenAPI 与实测请求一致，才能启动 Web。尚未交付的可选能力从首版范围移除，并在文档中说明，不由页面自行模拟成功。

**ZBA 交接包（06 提交、00 核对）：** 除真实 OpenAPI 外，还须提供兼容版本、认证和授权说明、全部已登记能力的管理支持矩阵、配置字段及生效规则、任务/审批/取消状态语义、恢复与幂等策略、安全合成样例以及对应契约测试证据。每项标明文档/测试的实际位置，不能只有“已支持”清单。07 发现契约与请求不符时交回 06 处理，不自行添加路由或绕过权限。

### 3. 后端验收后实现独立 Web，并完成 Beta 交付

**施工清单：**

- 在拟建的 `src/web/` 创建独立前端工程，依据冻结的 ZBA 契约实现 API 客户端、状态页、能力管理、配置流程、Agent 任务与审批；前端技术栈在本阶段确定。
- 统一未保存提示、字段错误、版本冲突和生效状态。任务界面从后端状态恢复，断线后查询终态或恢复事件；取消请求未确认时不能显示“已经取消”。
- 静态产物独立发布，生产网关提供同源 API 转发或经过验收的跨域配置。检查桌面与移动端、键盘操作、弹窗生命周期、错误重试和回归场景。

**Beta 验收：** 页面能够完成三条主线；刷新与重启不会把成功保存变成未保存；不把失败或未知结果显示为完成；普通用户无法越权；秘密不回显；显示层脱敏而标识保持原样；编辑真实名称时使用 `nameRaw`，避免将占位名写入配置。

**发布条件：** 后端与 Web 分别构建并记录兼容版本，完成回归及可验证的回滚演练，通过项目组发布验收后进入计划使用窗口。回滚只操作本次交付的产物或提交，不用强制 checkout 丢弃工作区修改。资源上限依据真实同机负载测量确定，内存、启动时间、构建时间和延迟均不能用未经测量的固定数字冒充验收结果。

**验收记录与签署：** 统一使用[执行总纲的交付模板](agents/00-orchestration-and-dependency-graph.md)，并补充前后端兼容版本和本次冻结范围；已批准文档不代表下表任何门禁已通过。

## 四、验收与待决策项

### 1. 首版用户验收矩阵

以下 PNL 编号用于需求追踪，不代表已存在或已通过的测试。全部使用合成数据；06 负责 ZBA 契约证据，07 负责 Web 行为证据，00 核对。Web 开工前必须通过的是后端对应部分，浏览器部分在 Wave 6 验收，不形成循环门禁。

| 编号 | 场景 | 可观察的通过条件 |
| --- | --- | --- |
| PNL-01 | 首次打开及状态请求失败 | 正确区分加载、空态、正常、错误和旧数据；失败不伪装健康；重试只读取 |
| PNL-02 | 能力待配置、停用或不支持动作 | 每个已登记项可定位，原因明确；不支持动作被后端拒绝，不因隐藏按钮代替授权 |
| PNL-03 | 修改多个配置后整批保存 | 单次提交绑定版本；全部通过才持久化；刷新/重启后与已保存版本一致，生效状态独立显示 |
| PNL-04 | 无效字段或两个客户端并发保存 | 错误定位且不部分提交；旧版本冲突不覆盖，草稿可修正或显式放弃 |
| PNL-05 | 保存已提交但应用失败、响应丢失 | 前者显示已保存但未应用/需重启；后者先核对结果，不把未知当失败并盲目重发 |
| PNL-06 | 未保存切页、关闭弹窗或会话失效 | 有明确草稿保护/放弃提示；重新认证不自动重发；秘密输入不进入持久化缓存 |
| PNL-07 | 提交工具任务及审批批准/拒绝/过期 | 任务标识稳定，重复提交不产生重复动作；审批绑定本次参数，拒绝或过期不执行 |
| PNL-08 | 取消与完成竞争、远端不响应取消 | 不冒报取消成功，不覆盖已完成结果；无法确认时明确未知及核对路径 |
| PNL-09 | 任务执行中刷新或断线恢复 | 恢复原任务状态，处理重复/遗漏事件；终态可查询，恢复不重做工具动作 |
| PNL-10 | 越权读取/写入与秘密处理 | 后端拒绝未授权请求；不返回受限任务/配置；秘密不回显，QQ 官方 Secret 无面板写入口 |
| PNL-11 | 脱敏编辑与不可信工具结果 | 显示脱敏、key 不变、nameRaw 编辑不写回占位名；原始载荷不默认暴露，脚本/HTML 不执行 |
| PNL-12 | 移动端、键盘及弹窗操作 | 三条主线可完成；焦点可见且可返回触发处，错误不只靠颜色；关键操作不依赖鼠标悬停 |
| PNL-13 | 独立发布、版本不兼容及回退 | 前端修改无需重编后端；不兼容时明确拒绝不安全写操作；兼容版本和回退演练有证据 |
