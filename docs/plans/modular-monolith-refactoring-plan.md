> 阅读顺序：本总规划 → [执行总纲](agents/00-orchestration-and-dependency-graph.md) → 当次任务手册。

## 一、为什么重构（Why）

当前项目是 .NET 8 常驻机器人服务，支持多平台接入、模型调用、工具执行及内嵌管理面板。重构目标是降低模块耦合、明确能力与配置边界，并为独立面板提供稳定后端，而不是重新实现已有功能。

### 1.1 已观察到的结构与问题

- Headless 项目仍嵌入 `wwwroot/**`，前端发布与后端产物耦合。解耦的收益需要实测，不能预先承诺编译耗时或常驻内存下降到固定值。
- 已有插件接口、平台适配端口、有限步进工具循环和配置发布机制。应先识别缺口再扩展，不能把现有系统描述成“完全不支持自然对话工具调用”。
- 独立 Core、Storage、Platforms、Model 工程已经存在，但“目录存在”“宿主采用”“回归通过”是三种不同事实。
- 文档曾把拟建接口和历史测试成绩写成完成状态。执行状态与证据现在集中到执行总纲，禁止依靠叙述或文件数量解锁下游。

### 1.2 约束与取舍

- 保持 .NET 8 模块化单体：核心服务在一个宿主进程内组装，不因拆程序集而拆微服务。
- 按低内存同机部署设计。工作区给出的约 1 GB 主机预算是部署约束，非本轮测量结果；Bot 进程及整机预算须在代表性负载下分别验收。
- 存储写入由应用统一协调；SQLite WAL 不是跨模块事务、配置版本控制或跨进程锁的替代品。
- 先交付完整后端，再开发独立 Web；“移除静态资源内嵌”不等于“删除 HTTP 管理能力”。
- CLI 只读。配置当前以数据库为真源，不能把编辑任意 JSON 后重启写成已支持流程。
- 保护现有功能、隐私边界与用户未提交改动；只用合成数据验证。

## 二、做成什么样（What）

### 2.1 已确认决策

| 决策 | 本版口径 |
| --- | --- |
| 工程形态 | 单宿主进程，按职责拆程序集；ZBA 由宿主承载 |
| 插件归属 | 首阶段放在 Engine 内部模块，不新建独立 Plugins 工程 |
| Web 前置 | 后端模块及 ZBA 首版契约验收通过，Agent-00 核对，负责人明确解锁 |
| ZBA 责任 | Agent-06 负责 ZBA 与宿主集成；Agent-00 负责共享文件合入和证据核对 |
| Beta 范围 | 状态、插件/驱动管理、统一保存、模型管理、任务与审批等，以面板规划范围表为准 |
| MCP 范围 | Wave 4 后端仍须验收；面板 MCP 管理页可延期；Docker 高权限管理不进入首版 |
| 日期 | 2026-10-10 至 2026-10-11 是有条件目标窗口，门禁未通过即顺延 |
| 未冻结项 | 新接口签名、路由、认证方案、前端框架及实测资源预算，在对应开工门禁评审，不猜测落地 |

### 2.2 目标工程及依赖

下表是目标，不是已完成清单。工程是否存在、是否已接入见执行总纲。

| 模块 | 职责 | 目标允许的项目引用 |
| --- | --- | --- |
| Core | 领域类型、平台/插件/模型/存储等端口 | 不引用其他业务工程 |
| Storage | 持久化实现、配置事务、秘密存取边界 | Core |
| Platforms | 平台协议、生命周期与消息适配 | Core |
| Model | 模型请求/响应、思考参数与传输 | Core |
| Mcp（拟建） | 协议客户端、工具投影与连接治理 | Core |
| Engine（拟建） | 回复、有限步进工具执行、内置插件、受控后台评估 | Core |
| Panel（拟建，ZBA 适配层） | HTTP 认证、DTO、管理及任务接口 | Core |
| Headless | 组装各实现、启动、健康、只读 CLI、停机 | 上述后端工程 |
| web（拟建） | 独立浏览器客户端 | 仅依赖 ZBA 外部契约，不引用 C# 工程 |

目标以端口驱动依赖：Engine 需要的平台、模型、存储及 MCP 能力通过 Core 契约注入；Panel 同样调用应用端口，不直接访问数据库。现有缺失端口由 Agent-01 与消费者协商，Agent-00 批准后补齐；上述依赖不能通过服务定位器或反射绕过。过渡期偏离须登记迁移项并在相应波次准出前消除。

```text
浏览器 web --HTTP/可选事件流--> ZBA（Panel）
                                   |
                              Core 应用端口
                                   |
                     Headless 注入 Engine 等实现
                       /       |        \
                 Storage   Platforms   Model / Mcp
                      所有业务模块向 Core 依赖
```

图表示调用与组装关系；编译依赖以表格为准。Plugins 是 Engine 内模块，不是额外程序集。

### 2.3 运行与配置边界

- Providers / Actions / Evaluators 是职责划分，不要求为了名称创建重复抽象。先迁移现有回复、工具门禁和后台处理路径，再补缺口。
- 禁用插件时不调度对应工具或外部服务；已经执行中的动作另有取消与结果核对规则，不承诺“绝对零计算”。
- 保留权限检查、发送审计、平台隔离和审批。自然语言请求不会自动扩大工具授权。
- 配置持久化成功后才发布；保存成功与运行时应用成功分开报告。全局保存需求由 Agent-01 定义事务边界，Agent-06 暴露为 ZBA 契约。
- 当前数据库、秘密仓储与环境变量各有边界。未来配置文件若作为导入入口，须经同一校验和保存服务；在导入能力验收前不得移除唯一可用的配置管理路径。
- 状态与诊断只输出安全元数据、计数及错误码。面板提供动作摘要，不公开隐藏推理或默认暴露原始工具载荷。

### 2.4 Web 交付边界

[面板规划](z-bot-panel-v0.1-beta-plan.md)是首版能力范围和用户验收的唯一来源；手册 07 负责执行，不再单独扩充市场、任意容器创建或远程部署范围。前端独立构建和发布；移除内嵌页面后，后端 API、健康和配置通路仍应可独立测试。

## 三、如何实施（How）

### 3.1 波次与交付

| 波次 | 执行角色 | 准出交付 |
| --- | --- | --- |
| 基线核对 | Agent-00 | 当前工作区、接口对照、测试失败归属和写权限确认 |
| Wave 1 | [Agent-01](agents/01-agent-core-and-unified-storage.md) | Core/Storage 接入证据，统一管理与保存契约 |
| Wave 2A / 2B | [Agent-02](agents/02-agent-platform-drivers.md) / [Agent-03](agents/03-agent-model-and-llms.md) | 平台及模型真实调用链迁移和回归；无冲突时可并行 |
| Wave 3 | [Agent-04](agents/04-agent-engine-and-gating.md) | Engine、内部插件、权限及受控后台任务 |
| Wave 4 | [Agent-05](agents/05-agent-mcp-ecosystem.md) | 冻结协议版本/SDK 后的 MCP 互通、治理及失败语义 |
| Wave 5 | [Agent-06](agents/06-agent-headless-cli-and-deploy.md) | ZBA、CLI、组装、静态资源解耦、跨工程护栏及后端验收 |
| Wave 6 | [Agent-07](agents/07-agent-modern-frontend.md) | 独立 Web、三条用户主线及 Beta 验收 |

Agent-06 在前期参与 ZBA 契约设计；Wave 5 是最终集成与验收，不是等到此时才发现缺失接口。Wave 1–4 的宿主接入通过 Agent-00 分批合入，避免只构建孤立程序集。

### 3.2 状态与证据

当前状态、写权限、基线命令和交付模板只维护在[执行总纲](agents/00-orchestration-and-dependency-graph.md)。本轮静态核对不赋予任何波次“已验收”状态。旧[评审记录](modular-monolith-review-2026-10-07.md)保留为历史证据，不修改成新测试成绩。

### 3.3 三道交付门禁

1. **模块准出**：新增/迁移模块被真实调用，适用行为测试通过；未完成项不会被下一波次隐式继承为完成。
2. **后端 → Web**：Wave 1–5、ZBA 必选范围、认证、保存事务、秘密处理、任务取消和状态恢复都有证据；Agent-00 核对，负责人解锁。
3. **Web → 正式使用**：独立构建、前后端兼容版本、合成回归、资源测量和回滚演练通过，负责人决定使用日期。

### 3.4 不以假精确代替验收

删除旧版固定文件数、固定断言数、启动 0.8 秒、构建 1–2 秒、回复延迟减半等完成承诺。先建立基线，记录负载、预热、并发、采样时长、进程/容器/整机口径，再确定资源和延迟预算。静态架构与隐私探针是必要检查，但不能独自证明端到端功能、生产安全或实际资源达标。

## 四、本版修订边界

本版保留“为什么、做成什么、怎么做”和后端先行方向，修正状态、接口、归属、门禁与安全语义。文档采纳不自动批准代码重构、删除旧面板、修改线上配置或发布；每次执行仍需明确任务范围。
