完成目标是：维护者可以走完上述关键路径，解释“已保存”和“已生效”的差别，在结果未知时找到安全的核对方式，并能根据状态与原因码处理故障。整体通过率、时延和成本是否达标，必须用范围明确的使用样本判断。

### 阶段二：本人现有 QQ 场景的 2–4 周验证

维护者选择一个可控范围，自行操作真实任务；Agent 与采集工具只接触允许的状态投影与汇总。开始前记录候选、启用功能、验证起止、任务类型和现有模型额度。沿用现有服务与预算，不新增付费基础设施。

**代表任务清单在开测前固定：**

| 类别 | 选样方式与预期 |
| --- | --- |
| 日常聊天问答 | 以现有 QQ 为主，由维护者选 1–2 个常用问题类型，注明应答/保持安静的条件、可接受等待及结果要求 |
| 只读查询/整理 | 选 1–2 个真实常用任务，在实际使用的 QQ `//` 与 Web 入口分别记录工具和结果判断标准；技术回归使用合成输入 |
| 需要审批的受控操作 | 先走已接 Runtime 的 Web 入口，选 1–2 个任务，副作用限定在测试目录或合成对象；明确获批前零执行、拒绝与取消的预期 |

清单只记录场景类别/编号、提交入口、预期行为、启用能力和观察方法，不写真实消息、成员或任务正文。清单覆盖正常路径与失败/恢复路径；调整任务类型时保留版本与原因。

QQ `//` 与 Web 任务维持现有链路，分别报告提交、完成、失败与可观察的取消/恢复结果。§4 的 Runtime 状态、审批、幂等与重启收口首先适用于 Web ZBA；QQ 入口按 D0 查明的实际能力列用例，不能直接套用 Web 状态保证。无法观测或未具备的能力列为缺口，由维护者判断是否影响选定的只读试用任务；审批受控操作留在 Web 入口。

1. **建立基线：**先在当前功能状态下记录一个覆盖主要任务类型的观察窗口，注明空样本和未观测时段；该窗口用于校准和后续对照。
2. **形成阈值：**取得基线样本后，维护者结合任务价值确认成功率、有用性、可接受等待和成本预算；同时固定有用性抽样方法，记录阈值版本、冻结日期和正式验收窗口。最终达标判断主要依据冻结后取得的新样本，基线用于诊断和前后对照，不作为唯一达标证据。失败后先调查，不通过调低标准获得通过。
3. **持续观察：**按天保存 §6 的安全摘要，按预先登记的 2–4 周计划观察；候选或重要配置变化时分段记录，受影响切片重新验证。不同候选/重要配置的达标样本分别判断，不通过合并掩盖差异，也不自动重置第 4 周的收尾日期。
4. **处理异常：**重复执行、越权、隐私暴露或不可恢复的卡住，立即暂停对应试用项并调查。保存受影响范围、原因码与恢复结果，不收集正文。
5. **形成结论：**输出是否值得继续用、最常见的三个阻碍、维护耗时、成本与证据缺口，按下方复盘节奏收尾。低任务量时只报告样本结论，不把日历经过当作稳定性证明。

**暂停后的恢复条件：**先消除停止原因，或排除相关能力并用对应验证证明缩小后的范围不再受影响；保留原反例并完成相应回归。恢复前核对候选、配置、可能仍在执行的任务及未决副作用，结果未知的原操作先核对，不换键重做。维护者据这些结果决定何时恢复、恢复哪些范围，记录日期与依据。暂停不会自动延长观察；到原定收尾时仍按现有证据给出结论，需补采时另定范围和结束条件。

**价值评价：**维护者按预先约定的抽样方法评价“解决了 / 部分解决 / 未解决 / 已放弃”，同时记录是否返工及大致人工耗时。按任务类别、入口列明抽样数、未评价数与标签分布，技术失败和放弃也纳入抽样，不仅挑成功任务。真实结果由维护者自己查看，观察材料只保留标签与计数。`Succeeded` 表示执行终态，不能替代“解决了问题”。

**复盘和结束：**每周集中检查一次安全汇总；第 2 周由维护者决定结束验证、继续到第 4 周、缩小范围，或先修问题。最迟第 4 周对固定候选、范围和阈值给出“范围内通过 / 不通过 / 证据不足”：适用指标及关键任务达标且没有未解决的停止条件，才可判范围内通过；已确认不满足约定标准则判不通过；样本、计量或本人评价不足则判证据不足。证据不足时明确缺什么、补采什么及新的结束条件，另定是否继续，不自动延长观察。

回复节奏保持默认关闭。#151 S6 在维护者选定的受控范围单独进行，先确认回复时机、打扰、漏回/重复、局部 Stop 与拥塞表现；本人决定启用时机。其结果与任务 Runtime 的完成率分别统计。

### 阶段三：根据使用结果做小范围可靠性改造

进入条件是已经观察到可复现障碍，或维护者为某一明确能力补充要求。一次只选一个优先问题，按“影响频率、影响程度、恢复耗时、改动风险”排序。

| 观察到的触发 | 优先改造方向 | 保持的边界 |
| --- | --- | --- |
| 保存结论难懂、核对入口不一致 | 收敛回执呈现和操作恢复控制 | 配置仍由唯一事务协调者写入 |
| 待批残留、取消误报、重连状态不清 | 修正生命周期投影和恢复流程 | Runtime 状态为权威，事件只触发重读 |
| 无回复难以判断原因 | 把连接、路由、应用状态与固定原因码串成诊断路径 | 复用现有 status、轨迹和安全日志 |
| 真实需要在 Linux 启用 Python 包 | 先复核精确候选已有 POSIX 证据，再补所选环境缺少的所有权、取消和进程清理验证 | 支持结论限定到已验证环境与能力；权限仍属宿主账户 |
| 同类改动长期跨越多个职责 | 对具体大文件先做 needs-design，再抽取一个边界 | 同一组回归证明行为等价，保留单一权威 |

阶段出口是被选问题的独立反例闭合、对应回归通过、恢复动作明确，再回到使用观察。需求稳定后才考虑外部 1–3 个试用方，企业定位、收费与托管由新的验证结果决定。

## 4. 第一阶段的验收场景

以下是必须检查的行为，先复用现有用例；缺失时才补独立测试。使用合成身份、模型、执行器与临时数据根。

| 路径 | 必须观察到的结果 |
| --- | --- |
| 正常保存模型配置 | 只提交变更字段；版本、持久化回执、当前运行状态能够区分；后续请求使用期望路由 |
| 版本冲突/非法配置 | 陈旧版本明确冲突；非法批次整体拒绝；当前配置不被部分覆盖 |
| 提交后运行应用失败 | 显示已持久化及失败的应用步骤/原因；提供核对与恢复指引 |
| 保存响应断开 | 保留原操作键；按原键查询，核对前阻止同目标换键重复提交 |
| 供应商热重建失败 | 真实展示 `model_projection_rebuild_failed`；不能承诺旧实例继续服务或重启必然解决 |
| 未获批的高风险任务 | 执行器副作用计数为零；批准后沿同一任务继续，拒绝/过期均有明确终态 |
| 取消及迟到结果 | 取消请求与取消完成分别展示；终态不被迟到结果覆盖 |
| 提交响应丢失 | 用原幂等键核对；已受理、未受理与无法证明三类结论分别呈现 |
| 事件缺口/重连 | 按 resync 重读任务、审批、状态及受影响资源；成功读取后再推进游标 |
| 宿主重启 | 原待批失效有原因；原运行中任务可为 Unknown；不会自动重做不确定副作用 |
| 鉴权变化 | 只读身份无写入口；锁定/过期及时清除秘密输入；旧身份迟到响应不影响新身份 |
| 界面本人验收 | 候选固定；提示能理解、恢复动作能找到；关键流程窄屏与键盘可完成，意见由本人填写 |

任务超时按当前投影判断：Runtime 的 `TimedOut` 对外可表现为 `Failed + timeout`，不要把所有超时归到 Unknown。重启产生的 Unknown 应有可解释原因；验收目标是追踪与处理原因，不能要求把它改写成成功。

取消或超时的任务终态不证明外部动作已经终止或撤销。D2 的恢复指引要分别记录任务状态与可验证的副作用结果；无法证明外部结果时保留未知并由维护者核对，沿用原操作关联，禁止据终态自动重做。

### 4.1 恢复范围表

| 中断场景 | 当前可依赖的机制 | 验收边界 |
| --- | --- | --- |
| 页面切换、组件卸载 | 普通草稿、按服务与身份隔离的最小待核对记录；迟到响应归属原操作 | 秘密输入及时清除，未决操作仍用原键核对 |
| 断连后同一页面恢复 | 原键 Find 与事件调度器的资源重读 | 不自动创建新意图或重放可能有副作用的任务 |
| 锁定、过期、换身份 | 清理令牌/草稿/秘密输入；最小未决关联按原身份隔离 | 只有重新取得对应身份权限后才能核对，其他身份不能借用 |
| 整页刷新、关浏览器 | 当前待核对注册表为内存状态，会丢失页面关联 | 明确提醒与人工核对路径；不承诺跨刷新自动恢复，不把普通回读冒充原操作回执 |
| 宿主重启 | 持久回执、任务台账与事件世代/高水位机制 | 按当前恢复契约收口；原键已知时核对，不确定任务不自动重做 |

跨浏览器刷新持久恢复只有出现明确使用障碍才另行设计，届时需独立确定保留哪些非秘密关联、保留多久及身份隔离方式。

## 6. 观察指标的口径

复用现有 ZBA status/tasks/approvals、轨迹安全投影、[metrics 实现](../../src/BotAgent.Headless/Adapters/Panel/WebUiServer.Metrics.cs) 与安全日志 feed。采集器只输出字段白名单与汇总，原始响应、任务正文、结果文本、会话/成员标识均不进入观察材料。

| 观察项 | 采集与统计规则 |
| --- | --- |
| 提交与任务结局 | 固定入口和样本集合（cohort），分别计提交尝试、明确拒绝、已受理、受理未知；按已受理集合记录终态、在途及原因码。执行成功率以已受理数为分母，端到端成功率以提交尝试数为分母，两者分别展示；跨窗口任务记录受理与终结时间窗 |
| 任务 Unknown | 独立记录首次出现、原因、存量及新增长；区分重启与执行结果不确定 |
| 审批残留 | 记录等待时长及批准/拒绝/过期/取消后是否收口；按配置有效期与执行期限判断 |
| 时延 | 端到端从客户端提交至观察到终态；审批等待从进入待批至退出待批；执行耗时从开始执行至终态。分布注明具体起止与时钟来源，同时列整个样本集合的完成、在途、Unknown 和计时缺失数，说明分位数只代表哪部分；未完成项不按零耗时计 |
| Token/成本 | 先证明用量覆盖所选入口及全部模型调用，再分别汇总已知输入/输出与未知用量。成本注明价格来源、日期与口径；覆盖或供应商用量不明时记任务成本未知，账单只作注明范围的总计 |
| 使用体验 | 维护者只写打扰、漏回、重复、恢复难度等结论与计数；不转录真实消息 |
| 结果有用性与返工 | 维护者按固定抽样标记解决了/部分解决/未解决/已放弃，列明抽样与未评价数、返工次数及人工耗时；与执行终态分开统计 |
| 运维负担 | 每周记录排障次数、维护耗时、需人工介入次数和未解决阻碍 |

以下边界决定指标是否可信：

- `/metrics` 的缓存用量 unknown 与任务 Unknown 是不同变量。进程计数器重启会归零，日汇总需标记进程世代。
- 现有 processing pipeline 的轮次 Token 计数不能直接归因给 Runtime 任务。先核对所选入口、辅助调用和故障转移是否纳入计数；不能证明完整关联时，保留任务成本未知，并分别列出聊天计数与账单覆盖范围。
- 轨迹归档主要保留慢/异常样本，不能用其分位数宣称所有请求的总体 P95。现有归档留存约七天，不能靠结束时的一次查询代表四周。
- 任务列表/台账有容量上限，事件也会发生缺口。先证明受控样本的受理分母和结局完整；不完整就标“样本/下界/未知”。只有实际缺少安全汇总时，才补最小聚合能力。
- 每日留存形状汇总，按候选与启用功能分段。成功率阈值在基线后确定；重复执行、越权、隐私暴露和不可恢复卡住沿用阶段二的停止条件。

## 7. 可信插件与后续触发条件

[SECURITY](../../SECURITY.md) 明确 .NET 插件在宿主进程内执行，permissions 是信息披露。Python [独立进程](../python-worker-protocol.md) 清理继承环境、绑定来源与进程所有权，但仍使用宿主账户的文件和网络权限；SDK capabilities 属协作检查。仅停用 .NET 插件也不能保证加载、构造或属性读取零代码执行。

本轮为每个获准候选记录来源、版本、SHA256、用途、许可证、权限声明、审核结论与回退位置。只有受信任且本人明确批准的包进入启用范围。治理状态不是安全背书；依 [M4](../plugin-market-m4.md) 撤销规则阻止后续获取，已安装实例由管理员检查正在执行的任务，再明确决定停用或移除。

| 后续事项 | 重新进入设计/排期的条件 |
| --- | --- |
| 不可信插件的 OS 权限隔离 | 实际需要执行无法信任来源的代码；先定义文件、网络、秘密与进程隔离契约，完成独立安全验证再开放 |
| 外部试用与企业定位 | 核心路径稳定、本人观察有价值，且存在愿意持续反馈的团队和明确任务 |
| 多租户/SaaS/计费 | 私有部署或外部试用证明需求，并确定租户与身份边界 |
| 多 Agent 协作、新平台扩张 | 已有流程无法满足具体任务，且能定义并发、责任与失败收口 |
| QQ 与 Web 任务生命周期统一 | 分入口验证发现可复现的体验或治理缺口；先明确台账、审批、取消、恢复与旧命令兼容契约 |
| 全站重设计、跨刷新恢复 | 明确使用障碍证明收益；另做流程与状态设计 |

### 9.2 D0 收尾判断

四部分齐全、已知事实可追溯、未知项有后续动作，即可交付 D0 清单，并明确下一步是“具备 D1 准备条件”还是“先补哪些证据”。D1 准备条件包括：目标源码与工作树确定、拟处理行为及调用链明确、写入范围/回归/回退方式可审查、影响该切片的未知项已解除。

D0 交付不要求先关闭全部历史专项，也不代表 D1 实施授权或阶段一验收。未影响 D1 的市场、全站视觉或其他平台缺口继续留在对应切片；影响 D1 的候选或契约疑点在实施前解决。D0 若确认现有行为符合要求，D1 任务卡可只安排缺失的验证与说明，按实际反例决定是否改代码。
