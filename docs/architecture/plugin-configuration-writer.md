# 插件设置与配置提交协调

插件设置提交与旧面板/ZBA 配置提交已经进入同一配置写入协调边界。活跃模块的新插件修订同时提交包值、作用域秘密、原键回执、全局配置版本和审计；任一步失败都会回滚整个 SQLite 事务。

P07 的已批准配置绑定现在复用原 settings JSON 作为唯一值载体，使用同一全局版本和协调器；九项原可编辑字段保留即时应用，绑定值不写入独立包 Overrides。普通未绑定包设置仍保留原重启采用行为。新配置声明要求 reader 11，安装、升级和卸载仍冷采用；独立页面与组合恢复保持 D2 待办。

## 实际提交链路

| 入口 | 协调 | 同事务事实 | 提交后的采用 |
| --- | --- | --- | --- |
| 旧面板/ZBA 配置 | `ConfigurationStore.SaveCore` → 真实 `SettingsStore.ConfigurationParticipant` → `SettingsBox` 发布锁 → 数据库写入者 | 原配置、秘密、全局版本、配置审计、回执 | 由原 `SettingsHotReload`/配置回执链发布快照和派生状态 |
| 活跃未绑定插件设置 | `PluginSettingsStore.Save` → `ConfigurationStorageBridge.CommitPackageSettings` → 同一参与者与发布锁 → 数据库写入者 | 包值、秘密、每包修订、HMAC 回执、全局版本、包设置审计 | 仍由既有准备戳与 `MarkApplied` 记录重启采用 |
| 已批准绑定插件设置 | `PluginSettingsStore.SaveBound` → 同一提交协调器 → `ConfigurationStore.PersistBoundConfiguration` | 原 settings JSON、来源模式、原键 HMAC 回执、全局版本、审计；包元数据只存 schema/修订与原空状态备份 | `PublishBound` 发布原设置快照；研究包通过当前代次读取，九项原即时规则不变 |
| 模块激活前的插件设置 | 同一内部提交入口 → 初始化锁 → 完整数据库事务 | 原启动期包值、秘密、每包修订、HMAC 回执 | 激活后仍可读取、原键核对并按原规则采用 |

接口只允许可信宿主持久化动作参加协调。包校验和包应用仍在通用锁之外；包无法获得数据库连接、完整 `SettingsBox` 或服务定位器。

## 写入与发布顺序

`SettingsBox` 持有原发布锁，覆盖旧配置的保存、快照交换和已存在的派生状态回调。活跃包提交也取得这把锁，因此不能越过已提交但尚未完成发布的旧配置。控制面直接使用 `ConfigurationStore` 时也遵守同一边界。

锁顺序为活跃发布锁 → 数据库写入者，或启动期初始化锁 → 数据库写入者。从初始化路径转入活跃路径时先释放初始化锁，再等待发布锁。已经位于数据库写事务中的调用在等待这些锁之前拒绝，避免数据库写入者与发布锁互相等待。

启动期判断与实际事务不能拆开。原双分支写法可能先判断“尚未激活”，随后配置模块完成激活，再由独立数据库路径保存包值，漏掉活跃全局版本。当前启动期提交在初始化锁内重新读取激活事实，并在同一边界完成事务；配置激活不能越过已经准入的启动期包写入。

## 版本、回执与失败

- 每包修订继续用于原比较并保存规则和兼容回执；它由同一写入者维护。活跃模块每个新的成功包修订将全局配置版本推进一次，因此持有旧全局版本的配置调用方会收到原版本冲突。
- 原键回执先于新修订检查恢复。重放返回原回执，不推进全局版本，不重复审计，不执行采用；更新后仍可核对较早的原回执。
- 包秘密、签名键、包状态、回执、全局版本和审计在同一事务内。秘密/审计故障或全局版本耗尽均不留下部分事实；清除故障后原键重试仍按原提交与回执规则处理。
- `ResolveRuntimeValues` 与 `MarkApplied` 继续核对精确包版本、schema 和修订。保存新修订后，旧准备戳不能标记为已采用；标记采用不会产生第二个配置修订。
- 未绑定包状态和 cfg wire 保持原契约。绑定声明覆盖完整 schema、owner/field/type/read-only/trim 和批准指纹；磁盘 Active/Previous/Pending 及实际 PE 读能力同步为 reader 11。任意属性或秘密不会因字段名匹配而暴露。

## 绑定值、代次与兼容载体

绑定读取在共享配置协调锁和同一数据库读取快照内取得 desired、runtime 和全局版本。`IPluginConfiguration` 只给包自己的不可变值；业务与控制各持有当前代次租约，未 Ready 或已退役时拒绝，卸载等待已进入读取结束。包规则和回调在配置锁外执行，锁内只有已完成校验的可信字段映射、持久化与快照交换。

旧面板修改与包设置修改彼此可见，原键重放不重复推进版本、审计或应用。绑定设置沿用原非秘密 JSON 键，不重写未知键、只读字段或无关秘密。以前默认研究包的准确空 schema 状态允许迁入，第一次绑定提交保留其原字节；其它不兼容包覆盖值拒绝迁移。提交失败整笔回滚，提交后应用失败保留 durable desired 和实际 runtime 差异，原键不重复执行。

## 快照文件发布

包安装状态、治理缓存与操作回执复用 Storage 的 `TextSnapshotFile`：同目录随机临时文件、完整写入与刷盘、发布前取消检查，然后原子替换。已有目标使用 `File.Replace`，允许具有 Delete 共享的读者继续读其旧快照；目标缺失时仅做非覆盖式首次移动。权限拒绝、非 Delete 共享占用及跨进程首次发布冲突仍失败，不加权限绕过或业务重试。此文件发布点不把多个文件与 SQLite 宣称为一个原子事务，组合恢复仍需 D2 协议。

## 可复核证据

`BotAgent.SettingsScopeProbe` 覆盖实际配置参与者和 SQLite 事务，包括原失败探针的二进制复跑、发布阻塞、嵌套写入、并发比较并保存、审计故障、版本耗尽、秘密回滚与过期采用戳。

`BotAgent.SettingsScopeProbe --configuration-startup` 在独立进程中控制真实数据库写锁，记录并复验配置激活越过启动期包提交的反例，同时验证启动值、原回执和激活后的第一个更新。

完整配置、插件生命周期、架构和合成宿主 HTTP 回归仍须针对最终候选运行。内部证据在工作区审查目录单独保存；这些检查不代替运行时页面、Linux/Docker、资源预算或完整 R2 验收。
