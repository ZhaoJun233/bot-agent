# 任务提交、审批、取消与恢复

适用入口：独立 Web 的任务页（Web ZBA / Agent Runtime）。QQ 的 // 指令和普通聊天按末尾能力表处理。

## 1. 提交没有得到可信回执

1. 找到这次提交留下的幂等键；在任务页选择核对，沿原键查受理记录。整页刷新后，重新连接原服务并使用原身份进入管理员模式，展开“核对先前的提交”，完整粘贴之前保留的原键，再选择“核对原键”。找到后可打开任务结果。程序接口为 POST /zba/v1/tasks/find，不能用新提交代替核对。
2. 分别核对受理事实、任务状态和能证明的工具结果。“已受理”只说明产生了任务，不能单独证明动作完成。
3. 根据下表处理。网络错误、HTTP 5xx 和查不到记录都不能证明没有执行；同一意图换键提交会产生新任务。

| 核对结果 | 能证明的事 | 下一动作 |
| --- | --- | --- |
| found / 已找到受理记录 | 原键对应稳定任务 id | 沿该 id 查看当前状态，不重提 |
| expired / 任务记录不可用 | 当前实例留有原键回执，但没有返回任务快照 | 保留关联并核对可用的操作收据；无法确认时请维护者处理 |
| accepted_unknown / 已受理但结果未知 | 原键回执来自另一进程实例，包括宿主重启前的实例 | 保留原关联，按原任务 id 核对恢复状态或独立操作收据 |
| unknown / 查不到受理记录 | 当前查询没有找到记录 | 保持未知；这不等于任务没有执行 |
| 服务端明确拒绝且能证明未受理 | 本次没有产生任务 | 修正拒绝原因后，由操作者决定是否建立新的提交 |

页面切换后可继续核对内存中的关联；锁定或令牌失效会清除秘密和请求内容，只在同一服务、同一身份下恢复最小未决关联。换服务或换身份时，旧响应不会补写到当前视图。整页刷新、关闭浏览器会丢失这份内存登记；已知原键时可按有权限的身份查询，原键丢失时先人工核对。

配置保存使用配置自己的原操作键与回执，参见 [配置核对说明](../architecture/model-configuration-apply-path.md)。普通配置回读不替代任务或保存操作的原回执。

配置页刷新后，可重新连接原服务、使用原身份进入管理员模式，展开“核对先前的配置保存”，完整粘贴自行保留的 cfg1: 操作键。此入口仅调用配置 Find；原保存仍在途或待核对时，先沿原来的“核对结果”入口处理。查询得到的持久化版本、应用状态及步骤描述原操作，不代表当前配置值或当前运行状态；请用“重新读取”查看当前情况。手动查询不会清空新草稿、解除其他未决操作或再次保存。操作键过期、代际变化或未找到回执时，按提示继续人工核对，不自动重存。

### 回执文件不可用

启动时已有任务回执文件无法读取、格式损坏或版本不受支持，宿主仍可启动和处理配置，但新任务提交返回 HTTP 503 / receipt_store_unavailable。原键查询保持 unknown；不能因此推断旧任务没执行。系统不会用新回执覆盖无法验证的旧文件。

先停止该宿主写入，保留故障文件，核对文件访问权限，并从兼容且可信的备份恢复完整回执；随后重启，由新实例重新验证。不要清空或删除回执来解除限制，也不要仅修复部分条目后丢弃其余历史。文件在运行期间被修复，不会直接解除当前实例的受理限制。

此保护不改变 512 条 / 7 天的保留窗口。首次安装没有回执文件时仍可提交；文件完全丢失与首次安装无法仅凭该文件区分，因此恢复时仍须一并保留兼容的任务台账、回执和相关状态备份。

手动核对不会提交任务，也不会恢复已经丢失的提示词、统计或浏览器关联。页面不保存核对输入到浏览器存储或 URL，切换身份、服务或离开任务页会清除；刷新前请自行保留原键。原键丢失时，只能从授权任务列表和已有操作收据继续核对。查不到记录、记录已清理和结果未知都不能证明任务未执行。

## 2. 审批和取消

受控操作先在 Web 任务页检查待批项、工具范围、有效期和原任务关联。有效工具作用域涉及 bash/write/docker 且审批开关开启时，任务先停在 WaitingApproval；未批准时不调用执行器。批准从同一任务继续，拒绝、过期或待批时取消会关闭这张审批，不复用旧审批重新执行。

| 当前状态 | 应如何解释 |
| --- | --- |
| WaitingApproval | 未获批，执行器尚未启动；批准、拒绝或取消都针对原任务 |
| CancelRequested | 已接收取消请求，仍需等待当前任务收口；不能宣称远端动作已撤销 |
| Cancelled | 本地任务已收口；待批阶段取消可证明执行器未启动，运行后取消仍需另核对副作用 |
| Failed，原因 timeout | 执行超时；内部 TimedOut 在 ZBA 中投影为 Failed，不表示远端动作一定没做 |
| Succeeded | 执行器报告成功；具体动作是否完成仍以可核对的操作结果为依据 |
| Failed | 任务失败；失败前可能已发生动作，不据此自动重做 |

取消后迟到的执行结果不覆盖已确定的终态。执行器是否收到取消、是否配合退出、远端是否已经执行是不同事实；缺少动作收据时保留未知。不要因为界面只显示失败或取消而自动再执行一次。

## 3. 断线、事件缺口与重启

1. 先保留原键和已知任务 id，等待重新连接，再从任务列表、审批列表和原键核对读取权威状态。
2. 事件流要求 resyncRequired 时，界面会整份补读必要资源；补读失败时保留旧数据并显示同步未完成，不能把收到游标当成已追平。
3. 宿主重启后的状态按下表理解，核对原记录和独立动作结果；不自动重放不确定的执行。

| 重启前状态 | 恢复结论 | 原因码 |
| --- | --- | --- |
| Queued | Cancelled | cancelled_before_dispatch |
| WaitingApproval | Cancelled，旧审批失效 | approval_lost_on_restart |
| Running / CancelRequested | Unknown | restart_state_unknown |

Unknown 表示本地无法证明远端执行到了哪一步。维护者先核对可以证明的副作用，再决定新的操作；旧记录、旧审批和“再次执行”按钮都不构成安全重放许可。台账不保存完整提示词、模型输出或任务结果正文；持久台账也有保留上限，记录缺失不证明未受理。

## 4. 三个入口的边界

| 能力 | Web 任务页 | QQ // | 普通聊天 |
| --- | --- | --- | --- |
| 原键受理与 Find | 有，核对同一意图 | 没有接入 Web 原键台账；重复指令可能成为新任务 | 没有 Web 任务受理键 |
| 受控运维前置审批 | 本轮使用入口 | 不把 Web Runtime 审批结论套到该路径；聊天工具的既有审批是另一层 | 不按运维任务处理 |
| 取消 | 请求与终态分别显示 | //stop 请求取消当前会话的服务器任务；回复“已让它停掉”不证明远端动作回滚 | 不宣称拥有任务页取消接口 |
| 状态核对 | 原键、任务 id、列表和操作收据 | //runs 核对本会话记录；//status 展示开关和路由配置，不是 Web Runtime 当前任务状态 | 按聊天自身的回复与错误处理 |
| 重启恢复 | 待批失效，已派发 Unknown，不重做 | 不承诺 Web 台账式原键恢复；记录不足时请维护者核对 | 不承诺 Web 任务恢复 |

验证时使用合成会话、假模型和隔离数据根。排障只看状态、固定错误码、计数与脱敏材料，不读取群聊正文、人物档案或原始协议报文。真实 QQ 接通和线上动作结果需要各自的授权及证据。

实现与契约见 [Agent Runtime 架构](../architecture/agent-task-runtime.md)；部署及数据恢复见 [Runtime 部署说明](agent-runtime-deployment.md) 和 [回滚预案](rollback-playbook.md)。
